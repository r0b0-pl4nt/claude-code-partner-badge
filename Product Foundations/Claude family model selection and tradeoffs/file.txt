The decision
Start with Sonnet, move to Opus for sustained reasoning tasks, and reach for Haiku when volume and cost dominate.
Most pilots start with Sonnet and expand from there. High-volume or high-autonomy use cases are where the model mix gets more deliberate.

Start fast (Haiku path)
High-volume or time-sensitive
Sub-agent pipelines, CI/CD scripting, rapid prototyping, cost-sensitive deployments. When throughput and latency matter more than reasoning depth.
Start capable (Opus path)
Complex or long-horizon tasks
Autonomous refactoring runs, multi-hour tasks, work where getting it right the first time outweighs cost. Sonnet handles everything in between.
The effort lever
Before you switch models, try adjusting effort first. It's a cheaper move.
The effort parameter tunes reasoning depth within a tier without switching models. On Opus 4.8, xhigh is available and is the recommended setting for coding and agentic work, often a better first lever than paying for a higher tier. On Sonnet 4.6, the parameter goes up to high, a useful lever before committing to Opus pricing. Writing unit tests for a 20-line utility function produces the same result at default effort as at extended thinking; a multi-file refactor with cross-module dependency analysis is where higher effort produces materially better output.

To remember
Model selection is an architecture decision; effort tuning is a performance lever. Know which you're reaching for before making a recommendation.

Match the model to the task type.
D · Sonnet 4.6 for all tasks
One model across the entire team keeps configuration simple.
Haiku works for simple, high-volume tasks, but complex refactoring, architectural review, and multi-step agentic tasks all require Sonnet or Opus. Using Haiku for everything degrades quality on the tasks that matter most to the client. The overnight autonomous runs in this scenario specifically need reasoning depth that Haiku cannot deliver reliably.
Opus is the right call for the overnight autonomous runs, but running 50 developers on Opus for routine feature work adds roughly 65% cost for no meaningful quality gain. Sonnet handles function writing, test generation, and documentation updates at a comparable quality level and at a fraction of the cost. Match the model to the work, not to a single ceiling.
Correct. Sonnet 4.6 handles routine feature work well at a reasonable cost. Opus covers the overnight autonomous runs where task complexity and duration justify the premium. This tiered approach gives the client cost efficiency on high-volume daily work while preserving reasoning depth for the tasks that need it.
Sonnet for all tasks is a safe default, but you're overpaying for high-volume scripted tasks that Haiku handles just as well. Haiku handles simple, high-volume tasks like docstring generation or inline completions at lower cost and lower latency, with no meaningful quality penalty for those use cases. Most enterprise teams do better with a tiered model than one model for everything.
